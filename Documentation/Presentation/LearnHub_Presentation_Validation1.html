1. Problématique & Solution LearnHub

Vision Métier

Le Problème Réel

  • Fragmentation des outils : Les apprenants alternent entre plusieurs sites pour lire des cours, acheter des formations et trouver des exercices.
  • Absence de suivi unifié : Difficulté d'évaluer concrètement ses lacunes et de mesurer sa progression en temps réel.
  • Manque d'accompagnement : Absence de tuteur personnalisé et isolement face aux difficultés pédagogiques.

La Solution LearnHub

  • Plateforme Tout-en-Un : Centralisation de la découverte, du paiement, de l'apprentissage et de la certification.
  • Parcours interactif & badges : Validation leçon par leçon, quiz d'évaluation et avis communautaires vérifiés.
  • Coach IA adaptatif : Génération automatique de plans d'étude personnalisés et mentor conversationnel.
Speech Oral (1 min) : "Aujourd'hui, l'apprentissage en ligne souffre d'un éparpillement des outils. LearnHub résout ce problème en intégrant tout le cycle d'apprentissage dans un écosystème cohérent, autonome et modulaire grâce à l'architecture microservices."

5. Architecture Technique Globale AWD

Spring Cloud & Docker
  • Frontend Web : Interface responsive unique consommant l'API Gateway.
  • Spring Cloud Gateway (:8080) : Point d'entrée unique, filtre de sécurité JWT, routage dynamique.
  • Netflix Eureka (:8761) : Découverte dynamique de services sans adresses codées en dur.
  • RabbitMQ (:5672) : Bus d'événements asynchrones pour le découplage temps réel.
  • Spring Cloud OpenFeign : Requêtes synchrones inter-services avec gestion de timeout et circuit breaker.
  • Conteneurisation Docker : Orchestration via Docker Compose de toutes les briques.

6. Données & Bases de Données Indépendantes

Pattern Database-per-Service
Règle Fondamentale AWD : Aucune Base Partagée

Chaque microservice est propriétaire exclusif de son schéma. Pour référencer une entité externe, on stocke un identifiant simple (ex: studentId, courseId). Aucun lien de clé étrangère inter-bases.

MySQL (identity) : User, Role, UserProfile, Permission
MySQL (course) : Category, Course, Chapter, LearningResource
MySQL (journey) : Enrollment, LearningProgress, LessonCompletion
MySQL (assessment) : Quiz, Question, StudentAttempt, Certificate
MySQL (marketplace) : Order, OrderItem, Payment, Invoice
MongoDB (community & coach) : Avis, Threads, Posts, StudyPlans
Speech Oral (45s) : "Pourquoi une base par service ? Pour garantir l'autonomie totale des équipes de développement, supprimer les blocages de verrous de base et permettre de faire évoluer chaque base indépendamment."

7. Interactions & Communications Interservices

Synchrone (Feign) vs Asynchrone (RabbitMQ)
Synchrone (OpenFeign)

Utilisé quand une réponse immédiate est indispensable avant de continuer.

  • Community ➔ Journey : Vérifier l'inscription de l'étudiant avant d'autoriser un avis (évite faux avis).
  • Journey ➔ Course : Vérifier que le cours existe et est publié avant l'inscription.
  • Coach IA ➔ Journey & Assessment : Collecter les progrès et scores pour le plan d'étude.
Résilience : Timeout 2s + Réponse 503 contrôlée
Asynchrone (RabbitMQ)

Utilisé pour les événements métier sans bloquer le client.

  • PaymentCompleted : Marketplace émet l'événement après paiement test ➔ Journey crée l'inscription.
  • ReviewPosted : Community publie l'avis ➔ Course met à jour la note moyenne du catalogue.
  • CertificateIssued : Assessment émet le diplôme ➔ Community attribue un badge d'engagement.
Résilience : Retry + Dead-Letter Queue (DLQ)
Speech Oral (1 min) : "Nous appliquons la règle d'or AWD : Feign pour une validation synchrone immédiate, et RabbitMQ pour tous les effets de bord asynchrones avec garantie d'idempotence."

8. Zoom Individuel : Marketplace & Billing

Présenté par Selim Hechmi (1 min chrono)
Mission & Entités Métier (Port 8085)

Gérer le panier d'achat, les commandes, les paiements sandbox et la génération de factures.

Entités JPA : Order, OrderItem, Payment, Invoice.

Contrats d'API REST :
  • POST /api/orders $ ightarrow$ 201 Created (Création de commande)
  • POST /api/orders/{id}/payments $ ightarrow$ 201 Created (Paiement simulé)
  • GET /api/invoices/{id} $ ightarrow$ 200 OK (Téléchargement facture)
Interaction Asynchrone Clé

Dès que le paiement est confirmé, mon microservice émet l'événement :

PaymentCompleted { orderId, studentId, courseId, amount }

Comportement en cas de panne : Si le service d'inscription est en panne, le message reste sauvegardé dans RabbitMQ. Le client reçoit son reçu instantanément.

Speech Individuel de Selim Hechmi (1 min chrono) : "Bonjour, je suis Selim Hechmi, responsable du microservice Marketplace & Billing. Mon service prend en charge la conversion des cours choisis en commande, le paiement sandbox et la facturation. Ses entités clés sont Order, OrderItem, Payment et Invoice. Mon endpoint principal POST /orders/{id}/payments valide la transaction en 201 Created et publie l'événement PaymentCompleted sur RabbitMQ. Cela garantit un découplage total : même si le service d'inscription subit une panne temporaire, le paiement de l'étudiant est sécurisé et l'inscription sera rejouée sans doublon."
